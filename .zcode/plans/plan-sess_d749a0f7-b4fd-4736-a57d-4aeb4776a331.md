# Backend Build Plan — Shriji Dealer Web

## Architecture Decision (final)
- **Database: Supabase (Postgres)** — plain SQL schema, free tier, managed; backend owns all credentials/JWTs (Supabase used ONLY as database, not Supabase Auth).
- **Backend: dedicated Node.js 20 service (Express)** in a new `backend/` folder — long-running process for cron jobs (5-min CRM poll, catalog sync), in-memory catalog cache, real rate limiting, horizontal scaling. Deploy target: Railway (India region available; Render is the fallback).
- **Vercel stays** for frontend + existing Zoho Commerce product proxy (`api/` untouched in Phase 1).
- **Ownership rule (invariant):** Zoho CRM owns dealer record + approval decision; Zoho Commerce owns products/prices/orders; backend owns logins/roles/staff/security; app only displays what backend returns.

## Phase 1 — Backend Build (`backend/`)

Folder structure:
```
backend/
  src/
    config/        env loading, constants
    db/            migrations (SQL), connection pool
    routes/        auth, dealers, staff, prices, webhooks, health
    services/      auth, dealerApp, crmClient, catalog, notifications
    middleware/    jwtAuth, roleGate, rateLimit, errorHandler
    jobs/          crmPoll (5-min), catalogSync, tokenCleanup
    utils/         audit, logger
  test/            unit + integration
  package.json     (own deps + scripts)
```

Build order:
1. **DB migration SQL** — your full schema on Supabase (uuid pk, FKs, jsonb, unique constraints: `dealers.zoho_account_id`, `dealers.dealer_code`, `users.email`).
2. **Auth core** — signup (password → argon2 hash), login, JWT access token (role, dealer_id) + refresh tokens (hashed), OTP issue/verify, `GET /me` (the endpoint the pending screen will poll).
3. **Dealer application** — save pending dealer + create Zoho CRM Account & Contact via CRM REST API (self-client refresh token flow, token auto-recovery same pattern as existing `api/zoho.js`).
4. **Approval webhook** — `POST /webhooks/crm/approval`: verify, dedup via `webhook_events` (payload_hash), refetch Account from CRM as source of truth, update dealer, notify; fallback `crmPoll` job every 5 min via `sync_state.last_crm_poll_at`.
5. **Staff invites** — generate code (hash stored), expiry, dealer approve/revoke endpoints, activation creates staff Contact in CRM.
6. **Price proxy** — `GET /api/prices` with JWT; role gate: dealer → dealer pricebook tier, customer → MRP only; serves from in-memory catalog cache refreshed by catalogSync job.
7. **Rate limits + audit log** on every mutating route; notifications service stub (email first, WhatsApp later).

## Phase 2 — Testing

- Unit tests (`node --test`, matching repo convention): auth flows, token refresh/revocation, invite expiry, webhook dedup, role gating on price proxy.
- Integration: run migrations against a Supabase test project (or local Postgres), exercise apply→webhook→approve flow end-to-end with a mocked CRM client + a real-CRM smoke test behind a flag.
- Negative tests: replayed webhook (must be ignored once), revoked staff token (must fail), customer hitting dealer price route (must get MRP-only), zero-price item → "price_on_request" flag (never ₹0).
- Load sanity: catalog cache hit path vs Zoho path.

## Phase 3 — Frontend Integration

- Replace demo auth in `src/data/session.js` with real JWT flow; tokens in Capacitor `Preferences` on native + httpOnly-ish pattern on web (never plain localStorage for refresh tokens).
- Screens: real Login/signup, "Apply as dealer" (GST + business form), "Staff login with code", dedicated pending-approval screen polling `/me`, dealer dashboard (generate codes, approve/revoke staff).
- Keep the crown-jewel `?from=` share-link + `viewerFor()`/`PriceBlock` customer-view logic untouched.
- Switch price display to backend proxy (server-side `priceFor` replacement — closes the current leak where `dealerRate` reaches the client).

## Phase 4 — Zoho Wiring (live)

- CRM checklist: create custom fields per §1 of the doc, Self Client + `ZohoCRM.modules.ALL`, refresh token in backend env only, approval workflow rule → webhook URL.
- Field mapping test with one real dealer application through to approval.
- Verify fallback poll catches a webhook miss.
- Only then decide whether to migrate the Zoho Commerce product proxy from Vercel into the backend service (optional, non-blocking).
